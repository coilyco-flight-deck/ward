# ward features

Inventory of what `ward` ships.

## Scope

Contributor-facing cli-guard gate: repo dev verbs, audit, ops, agent, and container surfaces.

## Commands

- **`ward exec <verb>`** - run a repo dev verb (`.ward/ward.yaml`) through cli-guard: argv-validated, one JSONL audit row, clean+synced gate. See [exec-verb.md](exec-verb.md).
- **`ward audit {path,tail}`** - read the audit log: `path` prints its path, `tail` streams rows (`--since`/`--follow`). See [audit.md](audit.md).
- **Ward's own crash reporting** - off-by-default GlitchTip-backed panic capture for the top-level `ward` Go process, keyed by `WARD_SENTRY_DSN` and redacted with the existing secret scrubber before send. It is explicit host-side crash telemetry only, not agent-run reporting, and it preserves the panic after flush so ward still fails loudly. See [error-reporting.md](error-reporting.md).
- **`ward git <verb>`** - audited passthroughs, concurrency-safe `commit`, destination-gated `clone` ([ward#285](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/285)), ephemeral-clone `grep`/`grep-remote` ([ward#369](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/369)), and pre-configured Forgejo auth on the network verbs (`fetch`/`pull`/`push`/`clone`) so they never drop to a username/password prompt ([ward#507](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/507)). See [git-verbs.md](git-verbs.md).
- **`ward setup`** - the live cache warmer / config doctor. It pre-bakes the selected runtime surfaces, reports the resolved source + SHA + cache path, and validates ops, exec, fleet, and smart defaults without building or replacing the ward binary. See [ward-setup-doctor-inventory.md](ward-setup-doctor-inventory.md).
- **GitLab forge adapter** - `WARD_FORGE=gitlab` switches the git host to a configurable GitLab base URL, routes issue comments through GitLab's native issue API, and uses merge-request landing language in the headless seed. See [agent-gitlab.md](agent-gitlab.md).
- **`ward exec lint-refs`** - lint issue refs in public-facing docs so every one resolves for a GitHub reader ([ward#446](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/446)): a terse `ward#123` never autolinks in a rendered Markdown file on the mirror, so `scripts/lint_issue_refs.py` (also a pre-commit gate) requires full-URL links and `--fix` rewrites them.
- **`ward hook pre-tool-use`** - Claude Code PreToolUse hook: binary-path check + bare-command deny with routing hints.
- **`ward agent director merge`** - the director's narrow PR-landing lane: scans open PRs in scope and merges only ward-owned ones whose linked issue thread says `workflow: pull-requests-and-merge`, requires `WARD-OUTCOME: merge-ready` before merge, carries a passed review summary, verifies the live PR head SHA still has the required branch status checks immediately before merge, and records `WARD-OUTCOME: done ✅` after the PR lands with the checked SHA and status context. Salvage and draft PRs stay out of bounds, and raw merge from a read-only director surface is refused.
- **Git host / tracker split** - ward's issue-thread surface is now a separate `Tracker` port from the git host. Forgejo and GitHub still default to paired host+tracker, and the Shortcut tracker adapter is now shipped for split-stack targets. See [compat-surface.md](compat-surface.md) and [shortcut-tracker.md](shortcut-tracker.md).
- **Director scratch policy** - director-style read-only sessions enforce the workspace clone as read-only and provision `/scratch` as the writable escape hatch for throwaway scripts and temp files. See [container.md](container.md) and [agent-surface.md](agent-surface.md).
- **`ward agent {engineer,director,advisor,qa} [--harness <name>]`** (public face: **`warded <role> <ref>`**) - startup-role roster: `engineer` implements detached, `director` a heartbeat surfacing a read-only session + triage comment trail, plus a separate `pull-requests` lane for open PR follow-up, `advisor` answers without code (a ref comments or fans cross-repo work into per-repo issues, trust-gated; [ward#424](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/424)), and `qa` is opt-in structured inspection that posts a verdict comment without changing implementation state. The semantic posture for those roles is the ward-owned `read` / `project-management` / `engineering` / `ops` / `admin` vocabulary, not a KDL surface tier ([agent-role-capabilities.md](agent-role-capabilities.md)). A startup role's host-cloud capability (AWS creds, the tailnet route) is still **guardfile membership in `ward-kdl.fleet.kdl`'s `roles` block**, not a first-class ward flag: the advisor and director hold the live-observe set (aws + tailscale guardfiles) and reach them with no flag - the director so its container joins the tailnet and can observe the live kai-server ([ward#547](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/547)) - the engineer holds none, and the demoted `--aws`/`--tailnet` survive one release as hidden back-compat aliases (`advisor --no-tailnet` is the isolation opt-out). The harness pick is spelled `--harness` or, equally, `--agent` (both first-class per [ward#660](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/660), neither preferred); its old spelling `--driver` survives one release as a hidden deprecated alias, and an explicit first-class spelling wins when the alias is also set. A tailnet-joining dispatch **readies the `ward-tailnet` docker network** before the pull: a host missing it has it **created** (idempotent), not a bare `exit 125` mid-launch, and an unattached ansible-owned `mac-proxy` box only **warns** (the run still launches, the SOCKS5 tower route just will not resolve until that infra role converges) ([ward#597](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/597)). The aws capability **exports the launching host's whole credential chain** (`aws configure export-credentials` - SSO, env, profile, assumed role, IMDS) and injects it as short-lived `AWS_*` env, so the run gets working creds regardless of how the host authenticates and with zero in-container chain replication ([ward#586](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/586)); it runs where the chain resolves (the launching host, a Windows broker host and the broker-forwarded director-surface path included). When export fails (AWS CLI v2 absent) ward falls back to a read-only `~/.aws` mount, which only forwards the host's identity - so when that fallback also finds no creds (docker would mount an empty dir, and `ssm` calls fail `NoCredentials` silently), ward prints a loud launch-time warning naming the fix rather than reading as delivered ([ward#579](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/579)). **Every** warded role (engineer, director, advisor, qa) auto-mounts the target's own `catalog.dependsOn` upstreams as **read-only** reference clones ([ward#573](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/573), widened from advisor-only): distinct from the writable `--repo` grants, deduped against them and the substrate set, and excluded from the reaper's push-verify ([container-multi-repo.md](container-multi-repo.md)). The set is resolved **in-container from the fresh clone**, never the host cwd ([ward#580](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/580)), so a dispatch from an unrelated working directory still mounts the *target's* deps. A `dependsOn` entry may be a **full git clone URL** for an external, non-Forgejo upstream ([ward#612](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/612)): its host + transport are honored (`ssh://git@github.com/...`), and **ward seeds the mirror itself host-side at launch** by cloning it over the **host user's default ssh keychain** (the ambient ssh-agent, then `~/.ssh` identities / `~/.ssh/config` - exactly what a plain `git clone` resolves, no ward-specific key) into the shared gitcache, then a `cp`-only helper lifts the finished bare mirror into the volume so neither the key nor any egress ever enters a container (never mirrored onto Forgejo). A dep that does not hydrate **fails loud** at launch instead of silently reading as present. Every role dispatches only for a trusted owner from the selected config bundle. See [agent](agent.md).
- **Global engineer concurrency cap** - host launches allow at most 10 running engineer containers at once, counted by Docker labels (`ward=true` + `ward.role=engineer`) before reservation so a full host fails fast with a `ward agent reap` recovery hint. `--print` and non-engineer roles are unaffected.
- **`--workflow direct-main|pull-requests|pull-requests-and-merge|patch-only`** *([ward#508](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/508), [ward#707](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/707), [ward#729](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/729))* - the dispatched engineer's **landing policy**: `direct-main` merges to `main` and closes; `pull-requests` carries work through a branch + pull request, then keeps watching the PR checks until they are green or genuinely blocked and, if that PR already exists when the run fails, mirrors the actionable failure comment onto both the linked issue and the PR while trimming reservation-lock wording from the PR copy; `pull-requests-and-merge` carries the same PR shape plus the director-merge marker and is not done until the merge lands; `patch-only` posts a branch with no PR or merge authority. PR workflows never ask the engineer to claim `done` at the PR boundary. Smart-defaults KDL can set a fleet default and per-repo overrides, with CLI `--workflow` taking precedence. The resolved mode shifts the seed, rides the container env + a `ward.workflow` label, and gates the cleanup path so a clean non-`direct-main` run is not misread as a failed `main` push. See [agent-workflow.md](agent-workflow.md) and [agent-director-pr-merge.md](agent-director-pr-merge.md).
- **`ward agent review` - the in-container code-review gate** *([ward#134](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/134))* - a pre-PR quorum gate the [engineer](agent-engineer.md) seed can wire into a headless landing run when explicitly enabled: after CI is green and before the run opens the PR or merges, the worker runs the review non-iteratively inside the container against the live filesystem state, loading the hand-curated aos code-review skill and starting with the worker's own harness family first. The gate is temporarily disabled by default in engineer seeds pending brokered QA, but `ward agent review` still runs directly for diagnostics. Other families remain as higher-cost fallbacks, and the gate no longer drops to advisory-only just because the worker's own family is the only one available. The gate is `CI green AND quorum >= threshold` and **fails closed** (a reviewer error, timeout, or empty vote blocks the landing, never passes it). The panel is **cost-tiered** - the worker family is the free tier run on every diff, other harnesses the paid tier run only as a tiebreaker or on a high-risk class - and the quorum **threshold tiers by an autonomy class** (`--review-class lint-cleanup|default|refactor`, riding in as `WARD_REVIEW_CLASS`: lint-cleanup passes on one reviewer, default a majority, refactor unanimous). `--skip-review` opts a run out, `--skip-preflight` skips both the pre-flight and the review gate, and the old `--no-review-gate` / `--no-preflight` spellings stay as compatibility aliases. The review summary is included in the final `WARD-OUTCOME` comment, and a skipped review is called out there too. For PR workflows, opening the PR is not the finish line: `pull-request` ends with `submitted` and `pull-request-and-merge` ends with `merge-ready`, then the director merge sweep records the final `done` after the PR lands. Each reviewer's structured verdict (verdict, reason, confidence) is persisted to a sidecar log beside the audit trail. See [dispatch-review.md](dispatch-review.md).
- **`--config` model-context overrides + startup config echo** *([ward#616](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/616))* - every warded run now echoes its resolved model-context config at container startup (a greppable `===== ward agent config =====` block: agent, model, effort/reasoning, endpoint, context-level), for every agent regardless of whether it writes a config file, so a run's harness config is visible in the log stream rather than silent. The repeatable `--config agent.<name>.<key>=<value>` flag overrides those knobs from the CLI, each dotted path translates to the matching `WARD_*` container env the entrypoint's `envOr` already resolves over the effective fleet default, and the director surface can forward it host-side. Per-role model/effort defaults now resolve too. See [agent-config-overrides.md](agent-config-overrides.md), [agent-flags.md](agent-flags.md).
- **Automation-mode dispatch ceiling** *([agentic-os#246](https://forgejo.coilysiren.me/coilyco-flight-deck/agentic-os/issues/246), [ward#607](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/607))* - a dispatch surface runs an issue only when `surface <= mode` on the order `headless > interactive > consult`. The gate lives in cli-guard's `resolveDispatchIssue` (the shared Dispatcher chokepoint), and ward's own dispatch path narrows that rule for engineer: `warded` / `ward agent` resolves issues through `resolveAgentWork`, never the Dispatcher, so the code-landing engineer role now refuses only issues explicitly labeled `interactive`; consult/default unlabeled issues dispatch normally, and `--force` / `--print` still override the refusal. The director and advisor roles are supervisory / consultative and ungated. Because it fires on `resolveAgentWork` (not the TTY pre-flight), the director's non-interactive headless auto-burndown is covered too. ward's forgejo and GitHub issue fetchers populate `Issue.Labels` so both gates can read the mode label; an unlabeled issue fails closed to `consult`, which still dispatches here until a deliberate interactive label appears. The mode labels (`headless`, `interactive`, `consult`) live at org scope beside P0-P4.
- **`ward agent reap`** *([ward#376](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/376))* - the host-side idle-killer: an engineer exits when done, so one still `Up` but log-silent past `--idle` (default 1h) is wedged. It `docker stop`s the running `ward.role=engineer` containers past the threshold (idle from the last container-log timestamp, else start time), unless a `--max-cpu` guard spares a busy one; interactive roles are idle by design and untouched. `--interval` runs it as a standing daemon, `--dry-run` previews. See [agent-reap.md](agent-reap.md).
- **`ward agent list [--json]`** *([ward#874](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/874))* - the director-surface inventory of running engineer containers: the host broker reports the active `ward.role=engineer` set, using labels first and reservation metadata where available, so a director can answer which run is carrying an issue without raw Docker access. The default is a stable human table, and `--json` emits the machine-readable schema. See [agent-list.md](agent-list.md).
- **`ward agent stop <ref>`** *([ward#627](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/627))* - the director-surface on-demand counterpart to reap's idle sweep: a director that mis-scoped an issue and dispatched an engineer against it can halt that specific run instead of commenting a correction and hoping it notices, or asking a human to `docker stop` host-side. It forwards a stop through the same dispatch broker (a new `Action:"stop"` on the request, back-compat with the launch default), and host ward resolves the target - `owner/repo#N` or a container name - and `docker stop`s the one match via the same graceful path reap uses. Stop-only, engineer-only: a target that resolves to any other role is refused fail-closed with its role named, and a ref matching zero or more than one engineer is refused with the candidates listed, never a blind stop. It runs only from a director read-only surface (broker addr set); off-surface it errors like a forwarded dispatch does. `--print` resolves + shows the target and stops nothing. See [agent-stop.md](agent-stop.md).
- **`ward agent logs <ref>`** *([ward#694](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/694))* - the director-surface on-demand counterpart to the mounted redacted archive: a director that needs one engineer run's logs can ask ward directly instead of reaching for a Docker socket or a host bind mount. It forwards a read through the same dispatch broker, host ward resolves the target to a live engineer container or a drained archive, and the source is reported before the body streams. Live containers prefer `docker logs` and support `--tail` plus `--follow`; removed containers fall back to the drained `~/.ward/agent-logs/<container>/console.log` archive or its redacted sibling. Ambiguous live matches fail loud, like `stop`. See [agent-logs.md](agent-logs.md) and [agent-surface-log-read.md](agent-surface-log-read.md).
- **`ward container {reap,bootstrap}`** *(hidden, entrypoint-internal; [ward#263](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/263))* - in-container plumbing: `reap` lands/salvages on teardown, records dispatch-time provenance, requires proof that the run landed new history after the reservation before it can read as done, re-checks the carried issue's same-repo closing reference on the already-landed direct-main fast path before it returns success, repairs a safely identified missing `closes #N` before final residual landing when possible, enforces that closing reference before `main` can land, treats an empty repo (no `origin/main`) as an establish-main case, posts a genuine salvage notice back on the carried issue, opens a salvage PR when PRs are available and links it from the salvage notice, dumps a structured `--- reap diagnostics ---` block to stderr + the salvage notice on every salvage/failure; the teardown also treats clean non-`direct-main` runs as done at their own boundary instead of failing them for skipping `main`, a dispatch version guard refuses to install a ward older than the dispatching host unless `--allow-ward-downgrade` is passed, and it verifies each `--repo` grant landed; the default substrate seed lives in aos, so ward-targeted runs read ward's docs and source from `/workspace/ward`, not `/substrate/ward`; `bootstrap` is the PID-1 entrypoint port. See [reap](container-reap.md) and [provenance](container-reap-provenance.md).
- **Reserving an issue road-blocks steering it** *([ward#494](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/494))* - a `ward agent` reservation makes the [reserved-means-immutable](agent-reserved-immutable.md) rule visible and, where the forge allows, enforced. The reservation comment shows one `WARD-RESERVATION: held` line, then collapses the directive - do not comment on or edit the issue to steer a run in flight, a correction goes to a new issue, dispatched fresh - and right after posting it the run best-effort locks the conversation where the API supports it: a GitHub-hosted run seals the issue (`PUT /issues/{n}/lock`) so a non-collaborator is blocked and a write-access architect meets a deliberate "unlock to comment" road-block, while Forgejo (no lock API, `is_locked` read-only) leaves the comment as the road-block and logs the skip. The lock never fails the reservation, and a pre-launch release unlocks again. See [reserved means immutable](agent-reserved-immutable.md).
- **Concurrent dispatches don't race onto one issue** *([ward#600](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/600))* - the reservation check and post are not atomic, so two `warded #N` on the same tick could each spin a container. Three guards close it: a broker per-ref lock serializes same-ref dispatches at the host dispatch broker before any container starts; a jittered reservation re-check is the in-container backstop for paths the broker doesn't cover; and a closed-issue skip no-ops with the `issue-closed` dispatch exit code instead of spinning a container to rediscover an already-landed issue, `--force` overriding. See [agent-reservation.md](agent-reservation.md).
**A failed run is self-documenting on the tracker** *([ward#609](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/609))* - a container that dies at the in-container [auth smoke gate](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/222) (stale host creds) is diagnosable from the issue thread, no docker logs required. The issue comments stay compact: one visible `WARD-RESERVATION` line, then collapsed details. Three surfaces carry that: the reservation comment folds the dynamic per-run seed context into collapsed details - resolved ref, branch, driver, run id, dispatch timestamp, workflow, and which thread comments were included vs stripped in the pre-flight read - referencing the static doctrine by ward version rather than pasting it, and carrying no comment bodies or issue-body text. The reaper's reservation-released comment names the specific gate that failed (`auth` / `ollama-probe` / `bootstrap`), folds in the error line, and gives the recovery step. The docker-log echo prints the same context as a delimited `ward run context` banner at entrypoint startup, before any gate, as the last-resort backstop. A pre-launch death is also loud and self-healing: the reservation-released comment leads with a `WARD-RESERVATION: released` line and a machine-detectable `<!-- ward-needs-redispatch -->` marker, and a `ward agent director` re-dispatches deterministically rather than relying on an incidental second attempt landing on a healthy host. See [agent-reservation.md](agent-reservation.md).
**Agent-run observability** *([ward#363](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/363), [ward#532](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/532), [ward#510](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/510), [ward#547](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/547))* - a detached `ward container drain-exit` waiter drains a run shortly after its container exits, so a just-closed run is observable at once rather than only when the keep-10 sweep evicts it; the sweep is the idempotent backstop, draining every exited run's console + transcript + secret-free `meta.json` before `docker rm`, and the release surface now keeps that local archive only. `WARD_AGENT_SINK` remains as the compatibility seam, but `signoz` and `both` are now inert labels while the optional OTLP/SigNoz ship path is deferred; ward also emits stable lifecycle lines during dispatch, bootstrap, and reap under a documented convention; the director read-only surface binds a disk-sink drain dir read-only at `/opt/ward-agent-logs` so a director reads run logs without a docker socket, and the director now joins the tailnet by default for live checks while the redacted drain archive remains the local post-run read surface. See [agent-observability.md](agent-observability.md).
- **`ward agents list [--json]`** - dump the effective fleet roster from `fleetconfig.Fleet` after ward's built-in frontier defaults, sparse bundle overrides, and role overlays resolve; `--json` is the stable read surface [agentic-os](https://github.com/agentic-os) (`aos`) reads ([ward#417](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/417)). See [agents-list](agents-list.md).
- **Selectable GitHub token source** *([ward#533](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/533))* - the GitHub dispatch lane provisions its token per `WARD_GITHUB_TOKEN_SOURCE`, defaulting to `env` (the publishable static-env-var path): `env` reads `WARD_GITHUB_TOKEN`/`GH_TOKEN`/`GITHUB_TOKEN`, `gh` mints a fresh token host-side via `gh auth token`, and `app` ([ward#534](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/534)) mints a short-lived, repo-scoped GitHub App installation token at dispatch: it signs an RS256 App JWT from a private key fetched from an operator-configured SSM param (`WARD_GITHUB_APP_ID` + `WARD_GITHUB_APP_KEY_SSM`), resolves the target repo's installation, and exchanges the JWT for a token scoped to that one repo. Resolution stays host-side and env-only in-tree - the App key's SSM param name rides an env var, never a baked path. See [agent-github.md](agent-github.md).
- **Audited raw Forgejo-token surface** *([ward#239](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/239))* - the plain `FORGEJO_TOKEN` is read only in a small, documented set of sites - the two resolver chokepoints (`forgejoTokenResolver`, `resolveForgejoToken`) every forge consumer funnels through, which try the [broker](broker.md) first, plus three root-only plumbing sites (broker daemon, entrypoint git-cred seed, reaper) that run outside the dropped-agent boundary. A build-time guard (`cmd/ward/forgejo_token_guard_test.go`) freezes that set: a new ad-hoc `os.Getenv("FORGEJO_TOKEN")` in any other file fails the build, forcing future forge access through a resolver rather than a fresh raw read. The full token-drop cutover ([ward#608](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/608), [ward#161](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/161)) stays blocked on a cli-guard read op; this keeps the surface from growing meanwhile. See [forgejo-token-audit.md](forgejo-token-audit.md).

- **Per-agent folders own their behaviour** *([ward#425](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/425))* - each harness is an `agentsapi.Agent` in `internal/agents/<name>/` owning its capability bodies; core dispatches through the registry by feature-test (no per-agent `switch`); a ratchet blocks its return. ## Spec-driven ops (`ward-kdl`)

`ward-kdl` is the build-time authoring layer ([docs/ward-kdl.md](ward-kdl.md)): permission surfaces + fleet configs for `ops`, `docker`, `agents`, `pkg` ([surface](ward-kdl-surface.md)), plus `ward-kdl.fleet.kdl`, the launch-selected smart-defaults bundle `ward-kdl.defaults.kdl`, and the staged container-topology overlay `ward-kdl.topology.kdl`. It builds into `ward-kdl-{read,write,admin}` tiers ([ward#240](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/240)) - not public artifacts ([ward#455](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/455)), authors build from a clone ([authoring](ward-kdl-authoring.md)). Two exceptions publish to an **internal** Forgejo package channel keyed to the release tag: `publish-kdl-write` pushes the `write` tier the broker reads ([ward#501](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/501), [broker.md](broker.md)), and `publish-kdl-read` pushes the `read` tier a sealed read-only director pulls for its non-mutating live checks ([ward#572](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/572)). The build reads its spec bundle straight from the tracked `.ward/ward-kdl/` tree (the assets-dir convention, [ward#453](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/453)); [examples/ward-specs/](ward-kdl-authoring.md#bring-your-own-specs) is the neutral swap-in starter. The shipped binary is **config-driven at launch** ([ward#653](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/653), epic [ward#650](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/650)): `WARD_CONFIG_REF` still drives the guarded edge surfaces, the runtime stamps the resolved bundle sha into audit rows there, and core agent/container runtime data stays ward-owned and baked. See [config-source.md](config-source.md).

The **exec-dialect** guardfiles auto-mount at their `wrap` path; `git` keeps a hand-written surface ([ward#284](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/284)), plus a **ward=true-gated** `ward docker exec` shell-into-a-run leaf ([ward#220](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/220), [ward-docker-exec.md](ward-docker-exec.md)). See [in-ward](ward-kdl-in-ward.md).

## Release pipeline

- **Release notes** *([ward#486](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/486))* - "does it affect you" verdict. [release-notes.md](release-notes.md).
- **Dual-forge binary matrix** *([ward#454](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/454))* - `ward-{darwin,linux,windows}-{amd64,arm64}` (windows as `.exe` + per-asset `.sha256` sidecar for scoop, [ward#561](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/561)) + `SHA256SUMS`, built once per tag and published byte-identical to both the Forgejo and GitHub release pages, so their checksums match. [release-binaries.md](release-binaries.md).
- **Push-not-poll package manifests** *([ward#571](https://forgejo.coilysiren.me/coilyco-flight-deck/ward/issues/571))* - the tag build writes every install channel: `bump-tap-formula` bumps the Homebrew tap to the tagged release binary and `bump-scoop-manifest` writes `bucket/ward.json` into the Forgejo scoop bucket at release time, so the daily autoupdate poll no longer lags. [release.md](release.md).
